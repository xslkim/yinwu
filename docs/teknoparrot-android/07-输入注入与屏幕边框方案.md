## 1. Windows 输入注入路线对比

### 1.1 背景：游戏通过哪些 API 读鼠标

Windows 游戏（含街机游戏的 PC 版、TeknoParrot 模拟层）读鼠标通常走三条路：

| 输入路径 | 机制 | 典型用户 |
|---|---|---|
| Windows 消息队列 | `WM_MOUSEMOVE` / `WM_LBUTTONDOWN`，或 `GetCursorPos()` 轮询 | 老游戏、部分 D3D9 游戏 |
| DirectInput 8 | `IDirectInputDevice8::GetDeviceState()`，相对位移为主，绝对坐标靠 `GetCursorPos` | 大量 DX9 时代游戏 |
| Raw Input | 注册 `RIDEV_INPUTSINK`，从 `WM_INPUT` 拿 `RAWINPUT`（带设备句柄 HID） | 现代引擎、对输入延迟敏感的射击游戏 |

街机光枪游戏（如 Haunted Museum、Ghost Squad、Operation GHOST 等）在 TeknoParrot 下，多数由 TeknoParrot 的钩子把鼠标坐标映射为 JVS/串口光枪数据，实际读的是光标位置 + RawInput/DirectInput 的按键，因此**注入的输入必须真实地移动系统光标**，只伪造消息通常无效。

参考：
- About Raw Input: https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input
- SendInput 函数： https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput

### 1.2 SendInput / mouse_event

**原理**：`SendInput()` 把 `INPUT` 结构插入系统输入流，注入点在 Win32 输入处理管线中——与硬件输入在"进入系统之后"汇合。它真实地移动光标、真实地产生按键状态，因此 `GetCursorPos`、`GetAsyncKeyState`、DirectInput、Raw Input 都能看到。

**关键标志语义**（`MOUSEINPUT.dwFlags`，见 https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput）：

- `MOUSEEVENTF_ABSOLUTE`：`dx/dy` 不是像素位移，而是 **0..65535 的归一化屏幕坐标**（映射到主显示器表面）。
- `MOUSEEVENTF_VIRTUALDESK`：把归一化坐标映射到**整个虚拟桌面**（所有显示器的并集包围矩形）。多显示器环境下必须加，否则坐标只覆盖主屏。
- `MOUSEEVENTF_MOVE`：移动。
- `MOUSEEVENTF_LEFTDOWN / LEFTUP / RIGHTDOWN / RIGHTUP`：按键。

**坐标换算**（1920×1080 光枪坐标 → SendInput 绝对坐标）：

```
sx = gun_x * 65535 / 1919      // 规范化到 0..65535（不是 /1920，右边界是 65535）
sy = gun_y * 65535 / 1079
```

多显示器 + VIRTUALDESK 时，要先取虚拟桌面几何：

```csharp
int vx = GetSystemMetrics(SM_XVIRTUALSCREEN);
int vy = GetSystemMetrics(SM_YVIRTUALSCREEN);
int vw = GetSystemMetrics(SM_CXVIRTUALSCREEN);
int vh = GetSystemMetrics(SM_CYVIRTUALSCREEN);
// 目标显示器内坐标 (mx,my) 相对虚拟桌面：
int dx = (int)Math.Round(((vx + mx) * 65535.0) / (vw - 1));
int dy = (int)Math.Round(((vy + my) * 65535.0) / (vh - 1));
```

**DPI 缩放坑**：注入进程若不声明 DPI 感知，`GetSystemMetrics` 等会返回缩放后的假坐标，导致映射偏差。必须在 manifest 或启动时声明 Per-Monitor V2：

```csharp
SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2);
```

**权限要求**：普通用户权限即可调用，但 UIPI（User Interface Privilege Isolation）限制：如果游戏以**管理员身份**运行而注入进程不是，消息/注入可能被静默丢弃。对策：注入进程与游戏同级提权运行，或要求 TeknoParrot 以普通权限运行。

**可见性**：对 DirectInput、Raw Input、消息轮询均可见（详见 1.7）。唯一问题：注入事件带 `LLMHF_INJECTED` / `LLMHF_LOWER_IL_INJECTED` 标记，**低级钩子（WH_MOUSE_LL）可以识别出来**，个别带反注入逻辑的游戏/反作弊会丢弃它。

**优点**：零驱动、零安装、纯用户态、C#/Python 几行代码搞定。
**缺点**：有 INJECTED 标记；不属于任何"真实设备"（Raw Input 里设备句柄指向系统鼠标，游戏若按设备过滤则无法区分；反过来说这也是优点——游戏把它当系统鼠标）。

### 1.3 Windows 消息注入（PostMessage）——为什么不行

`PostMessage(hwnd, WM_MOUSEMOVE, ...)` 只是往目标窗口的消息队列里塞消息，**完全不经过输入管线**：

- 不产生 Raw Input 的 `WM_INPUT`（Raw Input 由 RIT（Raw Input Thread）在收到设备输入时生成，PostMessage 与 RIT 无关）；
- 不改变光标位置，DirectInput 轮询 `GetDeviceState` 看不到任何变化；
- `GetCursorPos()` 结果不变；
- 只影响"直接从消息泵读 WM_MOUSE*"的程序，而游戏主循环通常用 Raw Input/DInput 轮询，根本不处理这些消息。

结论：**PostMessage 路线对 Raw Input / DirectInput 游戏一律无效**，只适用于自动化普通桌面软件。直接排除。

### 1.4 Interception 内核过滤驱动

**项目**：https://github.com/oblitum/Interception （API 说明见 https://deepwiki.com/oblitum/Interception/3.1-interception-api ）

**原理**：安装两个内核过滤驱动（keyboard filter + mouse filter），挂接在键盘/鼠标类驱动之上。用户态通过 `interception.dll` 打开设备上下文，可以：

- **拦截**真实键鼠事件（并决定是否放行）；
- **发送**伪造事件，这些事件在类驱动层"冒上来"，对 Windows 上层的一切（Raw Input、DirectInput、消息、低级钩子）而言**与硬件输入完全不可区分**——没有 INJECTED 标记，因为它根本不是从 SendInput 注入点进来的。

**API 骨架**（C，官方样例）：

```c
InterceptionContext ctx = interception_create_context();
interception_set_filter(ctx, interception_is_mouse, INTERCEPTION_FILTER_MOUSE_ALL);
InterceptionDevice dev = ...; // 鼠标设备号 11..20
InterceptionMouseStroke st;
st.state  = INTERCEPTION_MOUSE_LEFT_BUTTON_DOWN;
st.flags  = 0;
st.x = dx; st.y = dy;                 // 注意：相对位移
st.information = 0;
interception_send(ctx, dev, (InterceptionStroke *)&st, 1);
```

**权限要求**：安装驱动需要管理员（`install-interception.exe install`，见 https://deepwiki.com/oblitum/Interception/2.1-installation ），驱动带有效签名，Win10/11 无需关驱动签名强制。运行时进程不需要管理员（驱动内建的设备对象允许普通进程访问——这也是反作弊厂商诟病它的原因）。

**绝对坐标支持**：**不支持**。`InterceptionMouseStroke` 的 `x/y` 是相对位移，且 `flags` 只有 `INTERCEPTION_MOUSE_MOVE_ABSOLUTE`？——注意：**Interception 库的 flags 实际支持 `INTERCEPTION_MOUSE_MOVE_ABSOLUTE`（值 0x8000）**，但坐标域仍是虚拟桌面像素（非 0..65535），不同鼠标采样率下行为不一致，社区实测可靠性一般。工程上更稳的做法是：用 SendInput 发绝对移动，用 Interception 发按键；或者把绝对坐标差分成相对移动。

**抗检测性**：极高（事件来源与硬件相同）。但驱动本身有名字（"Interception"），个别反作弊按驱动黑名单封禁它；街机游戏无反作弊，不用担心。

**开源绑定**：C 原生；C# 绑定有 jasonpang/Interceptor、Yoticc/Interception.netfork（https://github.com/Yoticc/Interception.netfork ）。

### 1.5 虚拟 HID 设备驱动（ViGEmBus / vmulti / VHF 自研）

#### ViGEmBus 只支持手柄

ViGEmBus（https://github.com/nefarius/ViGEmBus ）是**虚拟手柄**总线驱动，只模拟 Xbox 360 手柄和 DualShock 4，**不支持鼠标/键盘/绝对指针设备**。项目已归档停更。对我们的鼠标注入场景**不适用**；仅当某款街机游戏只认手柄摇杆时才考虑。另外注意 HidCerberus（nefarius 的另一个项目）是"**隐藏**真实 HID 设备不被游戏枚举到"的工具，不是注入工具，方向相反，不要混淆。

#### vmulti（KMDF 虚拟多合一 HID）

- 仓库：https://github.com/djpnewton/vmulti （原始项目：https://code.google.com/archive/p/vmulti ）
- 基于 KMDF 的虚拟 HID 总线，一个驱动暴露多种设备接口：**相对鼠标、绝对鼠标/数位板（digitizer，带 0..32767 或自定义逻辑坐标的绝对 X/Y）、多点触摸、键盘、摇杆**。
- 用户态程序打开设备接口、写 HID 报告即可注入。因为 Windows 把它当真实 HID 设备，Raw Input 里会出现一个**独立的设备句柄**，事件无 INJECTED 标记，抗检测性最高。
- 缺点：驱动是测试签名（test-signed），安装需要开测试签名模式或自行重签；代码老旧（2015 年），需要自己维护编译；OpenTabletDriver 项目至今仍在使用它（见 https://www.reddit.com/r/XPpen/comments/1d4w2yk/ ），证明可用性。

#### VHF 自研（微软官方 Virtual HID Framework）

微软官方 KMDF 框架：写一个 HID source driver，向系统提交 HID read report，见 https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/virtual-hid-framework--vhf- 。WDK 自带 `vhidmini2` 样例。自研一个"绝对鼠标"只需：

1. 写一个数位板/绝对鼠标 HID 报告描述符（Usage Page = Generic Desktop，Usage = Mouse，X/Y 为 Absolute，Logical Max 65535）；
2. `VhfCreate` + 用户态 IOCTL 接收坐标，`VhfReadReportSubmit` 上报。

成本：需要 WDK 开发 + 驱动签名（EV 证书或测试签名）。工作量约 1-2 周，是"最干净"的终极方案，但第一阶段**不必要**。

#### 小结

- 要绝对坐标 + 完美兼容性：vmulti 或 VHF 自研。
- ViGEmBus 与本任务无关（手柄专用）。

### 1.6 各路线对比表

### 1.7 实测结论：SendInput 注入对 RawInput / DirectInput 的可见性

社区与官方文档的交叉验证结论（见 https://stackoverflow.com/questions/199687/ 、https://guidedhacking.com/threads/how-to-hook-directinput-emulate-key-presses.14011/ ）：

1. **Raw Input 能收到**：SendInput 注入的移动/按键会以 `WM_INPUT` 形式投递给注册了 Raw Input 的窗口，数据内容与硬件事件相同；`RAWINPUTHEADER.hDevice` 指向系统真实鼠标设备（没有独立设备）。少数游戏会调用 `GetRawInputDeviceInfo` 校验设备存在性，这种情况也满足（因为用的是系统鼠标句柄）。
2. **DirectInput 能收到**：DInput 的 `GetDeviceState`/`GetDeviceData` 基于与 SendInput 汇合之后的输入流，注入事件完全可见。大量自动化工具（AutoHotkey 的 SendInput 模式、串流软件 Moonlight/Sunshine 早期版本）都依赖这一事实。
3. **可被识别之处**：低级鼠标钩子（`WH_MOUSE_LL`）收到的 `MSLLHOOKSTRUCT.flags` 含 `LLMHF_INJECTED`（及 IL 相关的 `LLMHF_LOWER_IL_INJECTED`）；Raw Input 层面没有等效标志。只有专门装了低级钩子并检查该位的程序才能拒绝注入输入——街机游戏没有这种逻辑。
4. **已知例外**：个别 Raw Input 游戏对"光标被 SendInput 高频移动"的兼容性有 bug（如 Sunshine 分支 Apollo 的 issue #1479 报告 FiveM/GTA V 下鼠标损坏，根因讨论见 https://github.com/ClassicOldSong/Apollo/issues/1479 ），这类问题多与光标裁剪/相对模式有关，属于少数；街机光枪游戏（读绝对光标坐标）不在此列。

**结论：第一阶段用 SendInput 完全够用**；若实测某游戏拒绝注入输入，再升级到 Interception 或虚拟 HID。

### 1.8 推荐实现：120Hz 绝对坐标 + 按键（C#）

架构：UDP 收包线程 → 最新坐标槽（latest-wins，丢弃旧包）→ SendInput。不需要固定 120Hz 定时器——网络包到达即注入即可（光枪本来 120Hz 推送），按键事件立即注入。

```csharp
using System;
using System.Net;
using System.Net.Sockets;
using System.Runtime.InteropServices;

public class GunInjector
{
    [DllImport("user32.dll")] static extern uint SendInput(uint n, INPUT[] p, int cb);
    [DllImport("user32.dll")] static extern bool SetProcessDPIAware();

    [StructLayout(LayoutKind.Sequential)]
    struct INPUT { public uint type; public MOUSEINPUT mi; }
    [StructLayout(LayoutKind.Sequential)]
    struct MOUSEINPUT { public int dx, dy; public uint mouseData, dwFlags, time; public IntPtr extraInfo; }

    const uint INPUT_MOUSE = 0;
    const uint MOVE = 0x0001, ABSOLUTE = 0x8000, VIRTUALDESK = 0x4000;
    const uint LDOWN = 0x0002, LUP = 0x0004, RDOWN = 0x0008, RUP = 0x0010;

    // 画面映射参数：游戏窗口客户区（边框取掉后的有效区域，见第 2.5 节）
    public static int ClientX, ClientY, ClientW, ClientH;   // 屏幕像素，启动时由边框程序广播
    public static int BorderPx = 0;                          // 边框内缩像素

    public static void Inject(int gunX, int gunY, bool triggerDown, bool reloadDown)
    {
        // 光枪坐标 (0..1919, 0..1079) —— 其参考系是"含边框的画面"
        // 把有效画面区（去边框）映射到游戏客户区：
        double fx = (gunX - 1919.0 * BorderFrac) / (1919.0 * (1 - 2 * BorderFrac));
        double fy = (gunY - 1079.0 * BorderFrac) / (1079.0 * (1 - 2 * BorderFrac));
        fx = Math.Clamp(fx, 0, 1); fy = Math.Clamp(fy, 0, 1);
        int px = ClientX + (int)Math.Round(fx * (ClientW - 1));
        int py = ClientY + (int)Math.Round(fy * (ClientH - 1));

        // 归一化到虚拟桌面（单屏时 vw=1920, vx=0）
        int dx = (int)Math.Round(px * 65535.0 / (ScreenVirtualW - 1));
        int dy = (int)Math.Round(py * 65535.0 / (ScreenVirtualH - 1));

        var move = new INPUT { type = INPUT_MOUSE,
            mi = new MOUSEINPUT { dx = dx, dy = dy, dwFlags = MOVE | ABSOLUTE | VIRTUALDESK } };
        SendInput(1, new[] { move }, Marshal.SizeOf<INPUT>());

        if (triggerEdgeDown) SendButton(LDOWN); else if (triggerEdgeUp) SendButton(LUP);
        if (reloadEdgeDown)  SendButton(RDOWN); else if (reloadEdgeUp)  SendButton(RUP);
    }

    static void SendButton(uint flag)
    {
        var i = new INPUT { type = INPUT_MOUSE, mi = new MOUSEINPUT { dwFlags = flag } };
        SendInput(1, new[] { i }, Marshal.SizeOf<INPUT>());
    }
}
```

UDP 接收（latest-wins 模式，避免积压引入延迟）：

```csharp
var udp = new UdpClient(5555);
Task.Run(() => {
    var ep = new IPEndPoint(IPAddress.Any, 5555);
    while (true) {
        byte[] pkt = udp.Receive(ref ep);        // 包格式：[x:u16][y:u16][buttons:u8][seq:u32]
        // 若 seq 比上一次旧则丢弃；否则更新最新状态并 Inject()
    }
});
```

Python + ctypes 等价方案（原型验证用）：

```python
import ctypes, socket, struct
u32 = ctypes.windll.user32

class MOUSEINPUT(ctypes.Structure):
    _fields_ = [("dx", ctypes.c_long), ("dy", ctypes.c_long),
                ("mouseData", ctypes.c_ulong), ("dwFlags", ctypes.c_ulong),
                ("time", ctypes.c_ulong), ("dwExtraInfo", ctypes.POINTER(ctypes.c_ulong))]

def send_abs(x_norm, y_norm, flags_extra=0):
    mi = MOUSEINPUT(int(x_norm * 65535), int(y_norm * 65535), 0,
                    0x8001 | 0x4000 | flags_extra, 0, None)   # MOVE|ABSOLUTE|VIRTUALDESK
    # 组装 INPUT 联合后调用 u32.SendInput(...)，略

s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.bind(("0.0.0.0", 5555))
while True:
    pkt, _ = s.recvfrom(64)
    x, y, btn, seq = struct.unpack("<HHBI", pkt)
    send_abs(x / 1919, y / 1079)
```

注意：120Hz 下 SendInput 每次调用开销约几十微秒，完全无压力；不必合批。

## 2. 屏幕边框方案（Sinden 方案核心）

### 2.1 Sinden 官方软件怎么画边框

Sinden 光枪的定位原理：枪内摄像头拍摄屏幕，软件在屏幕四周画一圈白色边框，摄像头检测到边框四边/四角后透视解算枪口指向坐标。其 PC 软件的边框实现（据 Sinden Wiki 与社区文档）：

- 用**独立的置顶无边框窗口**画白色边框（而不是改游戏画面）；边框厚度、亮度可在软件里调节（"thin/medium/thick"、亮度滑条），并可保存/切换 profile；
- **对独占全屏（exclusive fullscreen）游戏无效**——Sinden Wiki 明确建议用 **Windowed Fullscreen（无边框全屏）** 运行游戏/模拟器（如 RetroArch 条目要求 "Windowed Fullscreen Mode ON"，见 https://www.sindenwiki.org/wiki/Retroarch ），或借助 Borderless Gaming 把独占全屏游戏改无边框（https://www.sindenwiki.org/wiki/Borderless_Gaming ）；
- 社区反馈（Reddit r/SindenLightgun）也证实边框本质是屏幕边缘的"大白框"，且玩家可以选细边框降低遮挡。

结论：**边框 = 置顶透明窗口，在 DWM 合成层盖在游戏之上；独占全屏会绕过 DWM 合成，边框必然消失，所以行业惯例是强制游戏无边框窗口化**。

### 2.2 自研置顶透明点击穿透边框窗口

技术选型：**WPF 单窗口**（`AllowsTransparency=true`）或 Win32 原生窗口均可。关键扩展样式（见 https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles ）：

| 样式 | 作用 |
|---|---|
| `WS_EX_TOPMOST` | 置顶，盖在游戏窗口上 |
| `WS_EX_LAYERED` | 分层窗口，支持透明/色键 |
| `WS_EX_TRANSPARENT` | **点击穿透**：鼠标消息穿过窗口直达下层游戏，绝不抢输入 |
| `WS_EX_NOACTIVATE` | 窗口永远不获得焦点，不打扰游戏前台状态 |
| `WS_EX_TOOLWINDOW` | 不出现在 Alt+Tab 列表 |

WPF 骨架（XAML + 后置代码）：

```xml
<Window x:Class="BorderOverlay.MainWindow"
        WindowStyle="None" AllowsTransparency="True" Background="Transparent"
        Topmost="True" ShowInTaskbar="False" ShowActivated="False"
        ResizeMode="NoResize" Focusable="False">
    <Border BorderBrush="White" BorderThickness="{Binding BorderThickness}"/>
</Window>
```

```csharp
protected override void OnSourceInitialized(EventArgs e)
{
    var hwnd = new WindowInteropHelper(this).Handle;
    long ex = GetWindowLongPtr(hwnd, GWL_EXSTYLE).ToInt64();
    ex |= WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW;
    SetWindowLongPtr(hwnd, GWL_EXSTYLE, new IntPtr(ex));
}
```

绘制参数建议：
- 边框宽度以**画面短边的百分比**配置（Sinden 默认约 1%~3%，1080p 下即 10~30px）；摄像头解算需要边框在画面内清晰可辨，太细识别不稳，太粗遮挡游戏；
- 白色用纯白 `#FFFFFF`；若担心烧屏/过曝可降为 `#F0F0F0`，但要保证与游戏画面的对比度；
- 提供热键切换边框显隐（调试与校准用）。

### 2.3 独占全屏（Exclusive Fullscreen）下覆盖失效与对策

**问题**：D3D9/11 的独占全屏（flip model 之前的 exclusive mode）下，前端缓冲直接交给显示驱动，**绕过 DWM 合成**，一切置顶窗口（包括我们的边框、Sinden 的边框、OBS 的游戏内叠加层）都不可见；强制置顶还会导致游戏闪屏/切回桌面。

**对策（按优先级）**：

1. **首选：强制游戏无边框窗口化（borderless fullscreen）**。DX9/DX11 游戏在无边框全屏下由 DWM 合成，性能损失在街机老游戏上可忽略，边框窗口正常显示。做法二选一：
   - 游戏自身/TeknoParrot 提供窗口化选项（见 2.4），再用 SetWindowPos 撑满屏幕；
   - 通用第三方工具：Borderless Gaming（https://github.com/Codeusa/Borderless-Gaming ，Sinden Wiki 官方推荐）、Special K 等。
2. 兜底：若某游戏独占全屏无法绕过（少数老 DX9 游戏切窗口会崩），可用 **OBS 式 hook 注入在游戏内画边框**（DirectX hook，在游戏 Present 前叠加绘制）——工程量大，第一阶段不做，留作备选。
3. 全屏独占 + 边框不可行时，也可以退而求其次：让手机端在**不接边框**的情况下按校准点定位（精度差，不推荐）。

### 2.4 TeknoParrot 侧配合与游戏窗口跟随

**TeknoParrot 配置**：
- 每个游戏 profile 是 `GameProfiles/*.xml`，其中含 `<Windowed>true</Windowed>` 字段（及分辨率相关字段）；在 TeknoParrotUI 的 Game Settings 里勾选 "Windowed" 即可让游戏窗口化运行（profile 说明见 https://teknoparrot.com 及社区文档）。部分游戏还有 `-w` 等命令行参数或 ini 设置，TeknoParrot 的钩子也会处理。
- TeknoParrot 目录中的 `HookedWindows.txt` 表明其钩子层会记录/识别已注入的游戏窗口信息——侧面说明**游戏窗口句柄是可被外部程序可靠识别的**（我们实测流程：通过游戏进程名 + `EnumWindows`/`FindWindow` 枚举顶层窗口，取客户区矩形）。

**窗口跟随逻辑**：游戏窗口可能启动时居中、分辨率切换时重建窗口。边框窗口必须动态跟随：

```csharp
// 方式一：轮询（简单可靠，30~60Hz 足够）
void FollowLoop(IntPtr gameHwnd)
{
    while (running) {
        RECT rc; GetWindowRect(gameHwnd, out rc);
        SetWindowPos(borderHwnd, HWND_TOPMOST,
            rc.left, rc.top, rc.right - rc.left, rc.bottom - rc.top,
            SWP_NOACTIVATE | SWP_SHOWWINDOW);
        Thread.Sleep(16);
    }
}

// 方式二：SetWinEventHook 监听 EVENT_SYSTEM_MOVESIZEEND / EVENT_OBJECT_LOCATIONCHANGE
// 事件驱动，零轮询开销，推荐产品化时使用。
```

找游戏窗口的稳妥顺序：启动 TeknoParrot 时记下游戏 PID → `EnumWindows` 找属于该 PID 的可见顶层窗口（排除无标题工具窗）→ `GetClientRect` + `ClientToScreen` 取客户区 → 边框窗口贴合客户区（贴合**客户区**而非整个窗口矩形，避免盖住标题栏；无边框全屏时二者相同）。

### 2.5 边框占画面内边缘的坐标映射问题

边框画在游戏画面**内侧** N px 时，存在两个坐标系：

- **手机端参考系**：摄像头看到的是"屏幕含边框的整体矩形"，光枪算法输出的是枪口相对**边框内沿**（或外沿，依实现）的归一化坐标；
- **游戏参考系**：游戏把客户区 (0,0)~(W-1,H-1) 当作瞄准坐标域。

二者必须对齐，否则瞄边会系统性偏移 N px。两种对齐策略：

**策略 A（推荐，与 Sinden 一致）：光枪坐标 = 边框内沿矩形 → 映射到整个客户区。**

设边框宽 b（像素），客户区 W×H。手机端输出归一化坐标 (u,v)（u=0 表示指着左边框内沿，u=1 表示指着右边框内沿），则注入光标的客户区像素坐标：

```
px = ClientX + u * (W - 1)
py = ClientY + v * (H - 1)
```

即：**边框虽然遮挡了画面外圈 b 像素，但瞄准域仍覆盖整个客户区**——指着边框内沿 = 指着画面边缘。这与 Sinden 官方行为一致（Sinden 的边框下瞄准边缘区域依然有效），玩家被遮挡的只是"视觉"，不是"可瞄准区域"。1.8 节代码里的 `BorderFrac` 即为此设计预留（若手机端输出的坐标系是"含边框整屏"，则先在手机侧或注入侧做一次 `(u' = (u - f)/(1 - 2f))` 的反归一化）。

**策略 B：边框画在客户区外。** 让游戏窗口比屏幕小 2b，边框占据四周不遮挡画面，瞄准坐标 1:1 映射客户区。代价是画面略小；对于 1080p 游戏窗口 + 大电视，视觉差异小，而映射最简单、无遮挡。适合窗口化（非无边框全屏）运行时使用。

第一阶段建议默认策略 A（无边框全屏 + 内侧细边框 1%~2%），因为它对所有游戏零配置差异。

### 2.6 替代方案简述：IR 标记 / 屏幕四角标记

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 白边框（Sinden） | 摄像头识别屏幕四周白框 | 零额外硬件；边框自带"屏幕在哪"信息 | 遮挡画面边缘；对游戏亮度/对比度敏感 |
| 四角 IR 标记（Aimtrak 式） | 屏幕四角放 IR LED，枪内 IR 摄像头定位 | 不遮挡画面；暗光下稳定 | 需额外硬件（LED 条）与供电；安装固定；移植性差 |
| 四角 QR/AprilTag 叠加 | 四角画小标记替代整圈边框 | 遮挡更小；标记带编码，多屏可区分 | 小标记识别对摄像头分辨率/对焦要求高；快速移动时易丢 |
| 无外标（校准点 + 姿态） | 开机打几个校准点建立映射 | 画面最干净 | 枪有位移/姿态漂移就要重校准，工程上最不稳 |

结论：**沿用 Sinden 白边框方案**——零新增硬件、生态已验证（TeknoParrot 社区大量 Sinden 用户），遮挡问题用细边框 + 策略 A 缓解。四角标记可作为后续优化项（遮挡更小）。

## 3. Android 端输入注入（第二阶段，次要）

场景：自研 Android 容器 App（Winlator 类：Box64 + Wine + 内置 X Server，容器代码自控）内运行 Windows 游戏，把 UDP 收到的瞄准坐标注入为容器内 Wine/游戏可见的鼠标输入。

### 3.1 Winlator 的输入链路（源码级）

Winlator（https://github.com/brunodev85/winlator ）的架构对自研容器有直接参考价值：

1. **Android 侧**：`XServerDisplayActivity` 承载一个自绘的 X Server 视图。触摸/鼠标事件到达 Android View 的 `onTouchEvent` / `onGenericMotionEvent`。
2. **容器内 X Server**：Winlator 用 Java 实现了精简 X11 Server（`com.winlator.xserver` 包），Wine 作为 X 客户端连到它。Android 输入事件被翻译成 X11 指针事件注入 X Server——核心调用形如 `xServer.injectPointerMove(x, y)` / `xServer.injectPointerButtonPress(button)` / `injectPointerButtonRelease(button)`（pointer 是绝对坐标，触摸板模式下自己做差分）。
3. **Wine 侧**：Wine 的 winex11 驱动通过 X11 协议（XInput2/核心指针事件）拿到指针移动与按键，再转成 Windows 消息/Raw Input 给游戏。也就是说，**只要事件进了 X Server，后续链路（Wine → 游戏）完全是标准路径，游戏不可能区分它与真实鼠标**。
4. Winlator 的虚拟按键/手柄层（`InputControlsManager` 等）也是殊途同归：最终都汇聚成对 X Server 的指针/键盘注入。

对自研容器的启示：**我们控制容器代码，最自然的做法就是在容器 App 内开一个 UDP 接收线程，直接把 (x, y, buttons) 以"绝对指针事件"喂给内置 X Server 的 inject 接口**（等价于 Winlator 的 `injectPointerMove`），按键映射为 X 的 button 1/3。无需 root、无需系统权限、对 Wine/游戏完全"可信"。

Java 骨架（容器 App 内）：

```java
// UDP 接收线程（容器服务内）
DatagramSocket sock = new DatagramSocket(5555);
byte[] buf = new byte[16];
while (running) {
    DatagramPacket p = new DatagramPacket(buf, buf.length);
    sock.receive(p);
    ByteBuffer bb = ByteBuffer.wrap(p.getData()).order(ByteOrder.LITTLE_ENDIAN);
    int x = bb.getShort() & 0xFFFF, y = bb.getShort() & 0xFFFF;
    int btn = bb.get() & 0xFF;
    // 坐标：光枪 1920x1080 规范 → X Server 根窗口坐标（即 Wine 桌面分辨率）
    float sx = x / 1919f * (xServer.screenInfo.width - 1);
    float sy = y / 1079f * (xServer.screenInfo.height - 1);
    xServer.injectPointerMove((int) sx, (int) sy);
    updateButtons(btn); // 边沿检测 → injectPointerButtonPress/Release(BUTTON_LEFT)
}
```

### 3.2 方案对比

| 方案 | 原理 | 权限要求 | 对 Wine/游戏可见性 | 结论 |
|---|---|---|---|---|
| **容器内 X Server 注入**（Winlator 方式） | App 内直接调 X Server inject 接口 | 无（自己代码） | 完全可见，走标准 Wine 输入路径 | **推荐** |
| MotionEvent 分发到容器 View | `view.dispatchTouchEvent()` 伪造触摸 | 无 | 可见，但触摸语义（相对/指针锁定）需处理 | 可用，略绕 |
| Linux uinput（容器 rootfs 内） | 写 `/dev/uinput` 造 evdev 设备 | 需 root（容器内 root 可行，但 Wine 走 X11 不读 evdev） | Wine 默认走 X11 输入，uinput 事件要再过一层 X 驱动 | 绕远，不建议 |
| Android 系统级 uinput | 在 Android 宿主造虚拟输入设备 | 需 root/内核权限 | 事件以真实触摸/鼠标进 App，再转 X | 需 root，收益与容器内注入相同 |
| `InputManager.injectInputEvent` | 系统 API 注入全局事件 | 需 `INJECT_EVENTS` 签名权限（系统 App）或 root/shell | 全局可见 | 普通 App 拿不到权限，除非定制 ROM/签名，不建议 |
| `adb shell input` 命令 | 系统 shell 权限注入 | 需 adb 常驻连接 | 可见 | 延迟高、频率低，120Hz 不可用 |

关键事实：
- `android.permission.INJECT_EVENTS` 是 signature 级权限（https://developer.android.com/reference/android/Manifest.permission#INJECT_EVENTS ），普通三方 App 无法获得；
- uinput 需要 `/dev/uinput` 写权限，标准 Android 上即 root（内核文档：https://www.kernel.org/doc/html/v4.12/input/uinput.html ）。

### 3.3 推荐

**首选：容器内 X Server 直接注入**（3.1 节方案）。理由：

1. 容器代码自控，零权限障碍；
2. 事件进入 Wine 的路径与真实鼠标 100% 一致，游戏侧（TeknoParrot-in-Wine 或 Windows 游戏）无任何兼容性问题；
3. 绝对坐标原生支持（X 指针本来就是绝对坐标），天然匹配光枪坐标；
4. 120Hz 频率对 App 内方法调用毫无压力。

第二阶段若要在 Android 电视上跑 TeknoParrot/Windows 光枪游戏，此方案与第一阶段的 UDP 协议完全复用——手机端无感知，只是接收端从 Windows 注入器换成容器 X Server 注入器。

## 4. 总体推荐路线图

| 阶段 | 输入注入 | 边框 | 备注 |
|---|---|---|---|
| 第一阶段 MVP（Windows + TeknoParrot） | **SendInput**（ABSOLUTE+VIRTUALDESK，120Hz latest-wins） | WPF 置顶透明穿透窗口 + 游戏无边框窗口化（profile `<Windowed>true</Windowed>`） | 1~2 天可出原型 |
| 第一阶段增强 | 遇到拒注入的游戏再引入 **Interception**（按键）或 **vmulti 虚拟绝对鼠标** | SetWinEventHook 事件驱动跟随；边框宽度/亮度热键 | 按需触发 |
| 第二阶段（Android 容器） | 容器内 **X Server injectPointer 注入** | 容器渲染层叠加边框（自绘，无置顶窗口问题） | 复用同一 UDP 协议 |

**关键风险与对策清单**：

1. TeknoParrot 以管理员运行而注入器非管理员 → UIPI 拦截 → 注入器同级提权；
2. DPI 缩放导致坐标映射偏移 → 注入进程声明 Per-Monitor V2 DPI 感知；
3. 游戏独占全屏导致边框消失 → profile 窗口化 + 无边框化（Borderless Gaming 兜底）；
4. 边框遮挡 + 坐标系不一致 → 策略 A 映射（1.8 节 `BorderFrac` 反归一化）；
5. 个别 Raw Input 游戏与高频 SendInput 不兼容 → 备选 Interception/虚拟 HID。
