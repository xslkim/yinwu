# 07. 订单绑定激活方案（代发模式下"只有我的客户能玩"）

> 前提决策（用户已定）：硬件采用 1688 一件代发，不碰库存与开模；
> 用软件手段把自研游戏绑定到自己店铺的订单，实现"只有从我这里买的人才能玩"。
> 本文是该决策的可落地技术设计。合规背景见 r2/r6 报告。

## 一、先解决核心矛盾：代发模式下怎么把"凭证"交给买家

代发意味着货从供应商仓库直接发出，你全程碰不到包裹。三条路径对比：

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A. 订单号激活（推荐主用） | 买家在 App 里输入抖店订单号+手机号后 4 位，服务端调抖店开放平台 API 验单后发许可 | 纯软件，零物料零人工成本；天然绑定"我的店铺" | 依赖抖店 API；订单号可能被转发分享（用设备数限制兜底） | ✅ 主方案 |
| B. 供应商塞卡（推荐备用） | 印一批激活卡寄给代发供应商，发货时塞入包裹（代发行规：塞好评卡/说明书通常免费或 0.1-0.2 元/单） | 不依赖任何 API；开卡体验好 | 要提前印卡、供应商漏塞需客服补发 | ✅ 作 A 的兜底 |
| C. 抖店虚拟类目发卡密 | 开通"虚拟充值/卡券"类目 | 官方路径 | 定向邀约，需企业满 1 年+注册资金 100 万+ICP 证——OPC 走不通（r2 已核实） | ❌ 放弃 |

**关键合规点**：商品本体是实物枪（白牌枪自带 SuperAR 等配套游戏，单独可玩），你的自研游戏在商品页表述为"附赠/加赠专属游戏权益"，不要把激活码当商品主体宣传——纯卖卡密会被认定虚拟商品下架（r2 结论），但"实物+附赠软件权益"是行业通行做法。

## 二、总体架构

```
买家下单（抖店）                      你的服务
   │                                    │
   ├─ 代发供应商发货（枪）               │
   │                                    │
买家收到枪，手机装你的 App/游戏          │
   │                                    │
   ├─ 输入订单号 + 手机号后 4 位 ────────▶│ ① 调抖店订单 API 验单
   │                                    │    （已付款/已发货/未退款）
   │                                    │ ② 校验该订单激活设备数 < 上限
   │◀──────── 签名许可令牌（JWT 式）──────┤ ③ 签发绑定设备的许可
   │                                    │
App 本地保存许可，之后离线可玩           │ ④ 定期轮询订单状态，退款→吊销
```

**技术选型（一人公司成本最优）**：

| 组件 | 选型 | 理由 |
| --- | --- | --- |
| 许可服务端 | 腾讯云开发 CloudBase 云函数 + 云数据库（免费额度内≈0 元/月） | 免备案域名、免运维；LeanCloud/阿里云函数计算亦可 |
| 订单核验 | 抖店开放平台"自用型应用"，订单查询 API | 自己店铺授权即可，不需要 ICP 证 |
| 许可令牌 | Ed25519 签名（私钥只在服务端），payload 含 orderId、deviceId、签发/到期时间 | 离线可验证、不可伪造 |
| 客户端 | Kotlin 许可模块（Android App/电视游戏）+ C# 许可模块（PC 游戏），同一套验证逻辑 | 你的两个技术栈各一个小库，<300 行 |
| 设备指纹 | Android ID + 可选绑枪的 BLE MAC | 防一号多机 |

## 三、激活流程细节

### 3.1 首次激活（联网，一次性）

1. App 引导页提示："输入购买店铺的订单号激活专属游戏"（附抖店订单号查找截图教程）。
2. 用户输入订单号 + 下单手机号后 4 位（防订单号被乱猜/爬）。
3. 服务端：
   - 调抖店订单详情 API，核对：订单属于本店、状态为已付款/已发货/已完成、**未全额退款**、收货手机号匹配；
   - 查许可表：该订单已激活设备数 < 2（允许手机+电视两台）；
   - 写入许可记录，签发令牌返回。
4. 客户端存令牌（Android Keystore/PC 注册表），进入游戏。

### 3.2 日常使用（离线为主）

- 游戏启动时本地验签名 + 校验设备指纹，**不强制联网**（电视/线下场景体验关键）；
- 每 30 天一次静默在线续验，失败进入 30 天宽限期，宽限期内仍可玩——避免服务器抖动误伤正版用户；
- 退款吊销：服务端每天轮询已激活订单的退款状态（或订阅抖店退款消息推送），退款成功→吊销该订单全部许可，下次续验时失效。

### 3.3 服务端接口（4 个就够）

```
POST /activate     {orderNo, phoneTail4, deviceId, gunMac?} → {token} | {error}
POST /refresh      {token, deviceId} → {token'} | {revoked}
GET  /health
（定时任务）refund-sweeper：轮询已激活订单退款状态，触发吊销
```

数据库两张表：`licenses(orderNo, deviceId, gunMac, issuedAt, status)`、`orders_cache(orderNo, status, paidAt, syncedAt)`（缓存抖店 API 结果，避免每单实时调）。

## 四、防破解与防分享（够用就好，别过度工程）

目标用户是直播间的休闲买家，不是破解组。做到这三层即可：

1. **签名令牌**：私钥只在云函数里，客户端只验签——改客户端只能绕过自己这台机器，无法生成新许可；
2. **设备数上限**：一个订单最多激活 2 台设备，超限要联系客服解绑（顺便制造服务触点）；
3. **退款即吊销**：把"激活后恶意退款"这条路堵死。

明确不做的：代码混淆军备竞赛、在线 DRM 全程联网、root/模拟器检测。这些投入大、误伤正版用户，对 129 元的休闲硬件套装不划算。

## 五、枪的 BLE 接入（让 30 元枪在你的游戏里能用）

白牌枪 = 手机支架 + BLE 按键板（BK 公版方案），无定位传感器——瞄准由你 App 的摄像头+IMU 负责，枪只出扳机/按键。接入步骤：

1. **买 2-3 款销量大的样品枪**（约 100 元），用 nRF Connect 或 Android HCI snoop log 抓 BLE 通信；
2. 大概率是两种情况之一：标准 BLE HID（直接当输入设备读）或私有 GATT characteristic（notify 几个字节，一位一个按键）——逆向工作量约 1-2 天/款；
3. 在 tvgun App 里加"外设触发源"抽象：屏幕触控 / 音量键 / BLE 枪 三选一；
4. 你的 App 支持后，**这把 30 元的枪在你的游戏里就是完整光枪**——这是套装溢价的来源，也是商品页的核心演示点。

注意：枪的 BLE 按键数据没有有效加密，技术上兼容不需要枪厂授权（r1 已论证），但商品页不要冒用枪厂品牌宣传。

## 七、风险与对策

| 风险 | 概率 | 对策 |
| --- | --- | --- |
| 抖店订单 API 权限收紧/审核不通过 | 中 | 备用方案 B（塞卡密，激活流程把"订单号"换成"卡号"即可，服务端同一套） |

| 服务器挂掉影响激活 | 低 | 离线宽限期设计；激活失败兜底客服人工发码 |
| 买家退款白嫖 | 低 | 退款自动吊销 + 抖店侧正常退货流程 |
